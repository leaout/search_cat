## 第二次核查

- 客户端根目录的 32 位 `DataBin.dll` 同时引用 `public/npc/NPCData.txt` 和 `Public/NPC/DynNPCData.txt`。
- DLL 导出了 `CNPCDataMgr::GetNPCOnMap(int)`。其返回类型符号是 `vector<CNPCData*>*`，这直接证明客户端数据层能够按地图 ID 取得 NPC 对象列表。
- `GetNPCOnMap` 的函数体读取 `CNPCDataMgr + 0x14/+0x18` 附近的索引结构，并按传入的地图 ID 查询；它本身不负责解密文件。
- `CreateDataBinMgr` 可在隔离的 32 位进程成功创建总数据管理器。其对象不是 `CNPCDataMgr` 本身，不能把该指针直接传给 `GetNPCOnMap`。
- 尝试调用总管理器的第二个虚函数发生访问冲突，说明其签名或初始化前置条件未知。为避免把错误调用当成解析结果，不再猜测执行未知虚函数。
- `DynNPCData.txt` 是 593 条可读定义记录，抽样字段包含碰撞框、资源/类型等数据；搜索地图 ID 23 和截图坐标没有形成有效关联，它不是静态 NPC 出生点表。

当前最有价值的入口已经缩小到：恢复总数据管理器到 `CNPCDataMgr` 的访问关系，或者静态分析 DLL 中加载 NPCData 的函数。自动寻路界面展示的 NPC 列表很可能正是通过 `GetNPCOnMap` 获取。

## 第三次核查：DataBin 解密与 NPC 表保护层

- 已从 `DataBin.dll` 的 `CNPCDataMgr` 加载函数定位到完整的解密调用。文件魔数必须严格为
  `3f 53 3f 47`（`?S?G`），随后跳过 4 字节，以固定 16 字节密钥
  `pleasebecareful0` 执行腾讯式 TEA 解密。
- TEA 块函数使用大端 32 位字、16 轮、初始和 `0xe3779b90`；外层包含随机填充、两字节盐和
  7 个零的尾部校验。新增只读验证工具 `tools/decrypt_qqsg_databin.py`。
- 用当前 `objects.pkg` / `update.pkg` 中的 `Achieve.txt`、`AchievePoint.txt`、`TaskDesc.txt` 做了
  独立验证：三者均为 `?S?G`，解密后尾部校验通过，记录首行分别为 908、983、647，文本结构稳定。
  这证明算法、密钥和包读取逻辑正确。
- 当前 NPC 表在三层包中都不是上述格式：`objects.pkg` 为 242372 字节、`combineUpdate0.pkg`
  为 247692 字节、`update.pkg` 为 251212 字节，三者魔数均为 `3f 3f 53 47`（`??SG`）。其
  4 字节后长度虽然满足分组要求，但用已验证的 DataBin 解密分支时尾部校验失败；常见的 2/4/8 字节
  分组换序也全部失败。
- `data/package.cfg` 证明客户端按顺序挂载基础包、多个合并更新包和 `update.pkg`。因此 NPC 表应以
  `update.pkg` 中版本为当前候选，但它仍使用 `??SG` 保护层，不是基础包版本过旧造成的单一问题。
- `CNPCDataMgr::GetNPCOnMap(int)` 的直接调用点先取得一个 NPC 对象，再将对象偏移 `+0x34` 的
  32 位值传给 `GetNPCOnMap`。结合导出函数语义，这为“`CNPCData + 0x34` 是地图 ID”提供了较强的
  结构证据，但尚不能据此命名坐标字段。

公开的旧版拆包器源码也只处理 `?S?G`：识别相同魔数后使用相同密钥解密；其维护者说明 2024 年后
客户端又对密钥/解包流程增加了保护并停止更新。因此该旧工具不能解释当前的 `??SG`。目前不能把
`NPCData.txt` 输出为可信坐标；下一步应定位当前客户端中 `??SG` 的生产/消费代码，或从游戏已加载的
`CNPCDataMgr` 做受控的只读结构验证。
